# iOS release pipeline — what the first upload taught us

> **Delete this doc when the pipeline lands.** What survives goes to
> [`apps/mobile/README.md`](../apps/mobile/README.md) (how to cut a build) and to the scripts
> themselves. This file exists to carry the findings from the first manual upload into the
> automated one, so the same evening is not spent twice.

**Status:** the first iOS build reached TestFlight on 2026-08-25 — `0.1.0-alpha.1`
(build `340027`) from `a7f83c6`, uploaded **by hand through the Xcode GUI**. Internal testing
works. Nothing about that path is scripted, and parts of it cannot be, in its current shape.

## What already landed

- **Version derivation** — `apps/mobile/app.config.ts` strips the pre-release suffix for
  `expo.version` and derives `ios.buildNumber` / `android.versionCode` from the clock. The repo
  keeps real semver; the stores see `0.1.0`. `pnpm test:versions` now fails if `app.json` grows
  a static build number, the same guard it already had for `expo.version`.
- **Store identity** — settled, and permanent: version scheme (`X.Y.Z-suffix` in the repo,
  numeric core to the stores) and build numbers (minutes since 2026-01-01 UTC). Both halves of
  the decision 04 was blocked on are now made and encoded.

## The finding that shapes everything else

**`apps/mobile/ios/` is gitignored and regenerated by `expo prebuild`. Everything Xcode wrote
into it during the upload is ephemeral**, including the two things that made the build possible:

| What Xcode wrote | Where | Survives a prebuild? |
| --- | --- | --- |
| `DEVELOPMENT_TEAM` | `project.pbxproj` | ❌ |
| `CODE_SIGN_IDENTITY` (must read `Apple Development`) | `project.pbxproj` | ❌ |
| Managed provisioning profile | `~/Library/…`, keyed to the project | n/a |

So a reproducible build **cannot read its signing configuration from the native project**. It
has to be supplied at invocation:

```sh
xcodebuild archive … DEVELOPMENT_TEAM="$APPLE_TEAM_ID" \
  CODE_SIGN_STYLE=Manual PROVISIONING_PROFILE_SPECIFIER="$PROFILE"
```

This is the same reasoning that put the version in `app.config.ts` rather than in `app.json`:
the generated artifact is not a source of truth, so nothing may originate there.

## Automatic signing is the wrong mode for a pipeline

The archive failed repeatedly with *"Your team has no devices from which to generate a
provisioning profile"* — while archiving, where **distribution profiles do not reference devices
at all**. The cause: with `CODE_SIGN_STYLE=Automatic`, Xcode resolves *both* profile types before
it will archive, so a gap on the development side blocks a distribution build. It was fixed by
registering an iPhone against the team.

Two consequences:

1. **A build machine has no phone plugged into it.** Automatic signing would fail there for a
   reason that has nothing to do with the build.
2. Apple's device list **resets only once per membership year**, so "just register the device" is
   not a strategy that scales past a personal machine.

⚠️ **The pipeline must use manual signing** with an explicitly created App Store distribution
profile. That also removes the dependency on which Apple ID happens to be signed into Xcode.

Corollary worth stating, because it cost an hour: `CODE_SIGN_IDENTITY` must be
`Apple Development` while automatic signing is on — Xcode rejects `Apple Distribution` there as a
conflicting manual override, and swaps in the distribution identity itself at export. Under
manual signing the identity is ours to set, which is the point.

## What the release script has to do

1. **Set the version**, if the release branch implies one — `scripts/set-version.mjs <version>`.
2. **Prebuild** with the build number pinned, so the artifact is reproducible from a commit:
   `LEAPSAKE_BUILD_NUMBER=<n> expo prebuild -p ios`. Without the pin, every prebuild invents a
   new number, which is right for a fresh upload and wrong for a rebuild.
3. **Archive** with signing passed in, per above.
4. **Export** with an `ExportOptions.plist` (`method: app-store-connect`, team, profile mapping).
5. **Upload** with an **App Store Connect API key** (`.p8`) rather than an Apple ID session, so
   it runs unattended. The credential shapes (`AuthKey_*.p8`, `*.p12`, `*.mobileprovision`) are
   already gitignored at the root — that was done preemptively in 04 and it holds.

None of this needs EAS, and **not depending on EAS is an owner decision, not an accident**
*(owner, 2026-08-24)*. 04's assumption that build numbers "belong to the EAS pipeline" is
superseded.

### Trigger

Owner intends `dev` as the long-lived branch, with `release/vX.Y.Z-etc` cut from it, and **the
release branch creation is what starts the pipeline** *(owner, 2026-08-24)*. Cut the branch and
the version bump together so the ref and the manifests cannot disagree. Time-derived build
numbers need no shared counter, so they stay monotonic across branches for free.

## Per-build friction to remove

- **Export compliance is asked on every upload.** The build sits at *Missing Compliance* until
  answered, and it blocks distribution to testers. Encoding
  `ITSAppUsesNonExemptEncryption` in `app.json`'s `infoPlist` retires the prompt — but only after
  the underlying question is answered properly. Leapsake implements standard algorithms *in the
  app* (XChaCha20-Poly1305, Argon2id, HKDF-SHA256 via `@noble/*`; AES-256 + PBKDF2 via
  SQLCipher), not merely OS crypto, so the honest answer to Apple's first question is *"standard
  encryption algorithms … in addition to"*. ⏳ **Open:** whether an EAR Category 5 Part 2
  exemption applies, and whether that carries an annual self-classification filing. Until that is
  settled the plist key cannot be set honestly. The France question is separate, answered
  per build, and follows the storefront list rather than the build.
- **dSYMs are missing** for React Native's prebuilt XCFrameworks (`React`,
  `ReactNativeDependencies`, `hermesvm`) — the upload warns, and crash reports will not
  symbolicate frames inside them. Our own code symbolicates fine. Decide whether to care before
  external testers generate crashes worth reading.
- **The app icon is Expo's default placeholder** — `app.json` sets no `icon`. Acceptable for a
  build only the owner installs; not for external testers, and certainly not for a listing.

## What each distribution tier actually requires

| | Review | Testers | Blocked on |
| --- | --- | --- | --- |
| **Internal TestFlight** | none | must be App Store Connect users (≤100) | export compliance only |
| **External TestFlight** | Beta App Review, ~1 day on first build | any email (≤10,000) | icon, beta description, "What to Test" |
| **App Store** | full App Review | public | icon, screenshots, privacy labels, age rating, support URL, the real version number |

The tiers are cumulative, and the pipeline should be able to stop at any of them. Note that the
external tier is the first one where the placeholder icon becomes a real problem, and the store
tier is where the version string stops being ours to reuse.

## Android parity

The same script should cut the Play build — that half is still entirely unbuilt, and Play's
**14-day closed-test clock only starts once a build is uploaded**, which remains the longest lead
time in v0.1. See [`v0-1_04_mobile-pipeline.md`](./v0-1_04_mobile-pipeline.md), which still owns
the Play half and the tester-recruitment problem.

## Acceptance

A signed TestFlight build produced from a clean checkout by **one command, on a machine with no
Xcode GUI session and no device attached**, with the version and build number derived from the
release ref. Same command, `-p android`, produces the Play upload.
