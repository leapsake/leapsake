# Leapsake v0.1 — the road to shipped apps

> **This is the table of contents for everything that must happen before v0.1, in order.**
> It holds the decisions and the sequence; the work itself lives in the numbered docs below,
> each of which is **deleted the day its work lands**. If you want to know *what to pick up
> next*, this file is the only place that answers it.

**v0.1 is:** signed, installable desktop and mobile apps a stranger can get, with a verified
backup story and an account system that cannot strand anyone. It is **almost** not feature work —
the product is built, with one deliberate exception (08, below). The posture this must not break
is [`../AGENTS.md`](../AGENTS.md) → *Product posture*.

## The two long clocks

Most of this is work you control. Two items are calendar time you cannot compress, and they
invert the obvious ordering:

- **Apple Developer Program enrollment** — days to weeks. Individual, $99/yr; accept that your
  legal name is the public seller name. Blocks notarization (05) and iOS submission (07).
- **Google Play production access** — a closed test with **≥12 testers opted in continuously for
  14 days**, which only starts *once a build is uploaded*. This is the real critical path, and
  it is why **mobile packaging (04) comes early rather than last**.

⚠️ **Reserve only what you will ship.** Apple's transfer criteria require an app to have at
least one released version to be transferable, so a reserved-but-never-shipped record cannot
move to an org account later — you would have to free the name and re-reserve it, with a race
window in between. Reserve "Leapsake" on both stores as soon as the accounts exist; names are
first-come-first-served.

**08 sits in front of 04 on purpose.** It adds a native config plugin and two OS permissions
(iOS notifications, Android `POST_NOTIFICATIONS`), and 04 is where the first EAS build and the
first store listing are cut. Landing it after 04 means a second store-metadata pass in the middle
of the Play clock, which is the one window you least want to touch.

```
Accounts     ├─ Apple enroll ────────┐              ┌─ iOS submit ─┐
             └─ Play enroll ─┐       │              │              │
Mobile         08 ─ 04 ──────┴─ 14-day closed test ─┴──────────── 07
Desktop             05 ─ 06 ────────────────────────────────────  07
Web spike    (any time, ideally before 04)
```

## The decisions this encodes *(settled 2026-07-21)*

| Decision | Choice | Consequence |
|---|---|---|
| Developer account type | **Individual**, both stores | Cheapest start; legal name is public; Play's 12-tester/14-day wall applies |
| Eventual org move | **Yes, early** — via app transfer | Preserves installs/reviews/bundle IDs, but **not key custody** — see [`@leapsake/key-custody`](../packages/key-custody/README.md) |
| Bundle IDs | `com.leapsake.app` · `com.leapsake.desktop` | Permanent after first publish. `.app` is form-factor-neutral so a future iPad/watchOS target joins the same Apple record; it also survives an RN→native rewrite. Electron stays a separate identity — Universal Purchase would require the Mac App Store and cost `electron-updater` |
| macOS distribution | **Direct download**, notarized, not Mac App Store | No review latency; auto-update is ours; MAS sandbox pain avoided |
| Release gate | **Local script** over `pnpm test:all --strict` | Real keychain, $0, honors testing principle #6; hosted CI is an *additional* PR check |
| Repo visibility | **Public at (or shortly before) v0.1** | Unlocks free macOS Actions runners; requires the pre-flight in 07 first |
| Versioning | **Everything stays `0.0.0`** until needed *(owner, 2026-07-31)* | The real deadline is 04's first store upload, not the v0.1 cut — see 04 |
| Notifications in v0.1 | **Yes, mobile only** *(owner, 2026-08-14)* | The single feature-work exception. Every other channel (email above all) is out of scope for v0.1, so without it a reminder cannot reach a user who isn't already in the app — see 08 |

**Corollary: keep the org move early.** Blast radius scales with user count at transition.

## Open decisions for owner sign-off

1. **How much of the E2E catalog gates v0.1, really?**
   [`v0-1_06_e2e-and-release-gate.md`](./v0-1_06_e2e-and-release-gate.md) → *The release-gate
   policy* currently requires the **full catalog green on iOS + Android + macOS**. Taken literally that
   is plausibly the single largest chunk of remaining work — larger than all of distribution.
   Options: (a) honor it fully; (b) amend to *full catalog on macOS + the existing driver
   self-test plus a smoke subset on mobile* for v0.1, with the full mobile catalog as a
   fast-follow. **Leaning (b)** — but it is a deliberate amendment to a written gate, so it
   needs your call rather than a quiet reinterpretation. Decide before 06.
2. **Flows 6/7a in the v0.1 gate or fast-follow?** Follows from (1). See 06.
3. **Auto-update before or after going public?** Public-first is simpler; interim tokens work
   if you want updates sooner. See 05 and 07.
4. **Play closed-test tester recruitment** — 12 real humans for 14 continuous days is a real
   logistics task for a solo bootstrapper. **Start the list now**, not at 04.
5. **Does v0.1 ship without merge by recovery phrase?** Deferred while building the merge
   *(owner, 2026-08-08)*. `recoverAccount` refuses a device that already holds an account exactly
   as `joinAccount` does, so merging by phrase needs the same copy-first treatment and is a second
   full flow on both clients. The gap: a user who has their account's **phrase** but not its
   password must recover on their *other* device first — which is fine unless that device is the
   one they lost. **Leaning ship-without** (password-plus-a-second-device covers the realistic
   case, and the flow it would duplicate is the most delicate one we have), but it is a real hole
   in the "cannot strand anyone" promise, so it is your call. Context:
   [`encryption/model.md`](./encryption/model.md) §7.2.2.

## Explicitly not v0.1

Everything else lives in [`v0-2.md`](./v0-2.md) — including work that is *ready* and merely
non-blocking (vCard export, reminder search, dedup quality, the onboarding import nudge). The
rule is strict on purpose: **if it does not gate v0.1, it waits.** That is what keeps this list
short enough to finish.

**08 is the one exception, and it is written down as one** so it cannot be cited as precedent: a
reminders app with no way to reach a user outside the app is not shippable, and email — the
obvious alternative channel — is itself out of scope for v0.1. Notification *privacy levels* and
the *desktop* applier both stayed behind the rule; see 08 → *Scope*.

**Out of scope entirely for v0.1:** Windows and Linux desktop, matching the E2E host policy —
blocked, not waived. Windows code-signing certs carry their own procurement latency and, for
OV/EV, hardware-token logistics.
