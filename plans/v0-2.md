## Reconciliation — dedup and merge quality

How the built parts work is in [`../packages/core/README.md`](../packages/core/README.md).

- **Fuzzy / typo-tolerant name matching** — the scorer's reserved `"low"` tier, via
  `fastest-levenshtein` or `cmpstr`, entirely inside `duplicate-score.ts`'s `sameFoldedName`
  predicate. No caller or API change.
- **`libphonenumber-js` phone normalization** — E.164 canonicalization; its own increment.
- **Pets / generalized `mergeEntities`** — a small follow-on; the reference graph is already
  entity-typed.
- **Bulk-import dedup.** Today `ingestContacts` creates every accepted contact unconditionally,
  so importing an overlapping list produces duplicates _after the fact_. Mostly A+B reuse: score
  each parsed contact against the existing set before the review screen renders. The seam exists —
  `ImportDecision.action` is an enum with `create` and `skip`, and this adds a third arm pointing
  at an existing person. **Must honor the `not_a_duplicate` memory**, or a pair the user already
  dismissed comes back on every import.
  > ⚠️ **The import nudge shipped first** _(owner, 2026-09-10)_, so this is now the second half of
  > a first run rather than a refinement: the getting-started step sends a brand-new user straight
  > into an import, and every duplicate it creates lands on a Home that has barely anything else
  > on it. Suppressing the duplicates nudge for a window instead is a **trap, not a dial** — its
  > id is content-addressed on the pair set, so reporting no pairs tombstones that exact id and
  > the same set re-deriving later never comes back.

_Open:_ **survivorship granularity** (v1 keeps the survivor's scalar fields wholesale; a per-field
picker is deferred — revisit if users hit it) and **concurrent merges** (two devices merging

## The user model, where the build has not caught up

The intended destination is recorded in [`@leapsake/key-custody`](../packages/key-custody/README.md)
→ _The product model this serves_. These are the parts the code does **not** yet do — conscious
deferrals, not surprises.

- **Multiple authenticated users per client, with per-user data isolation.** Today a client is
  implicitly single-user. Hosting several needs one store per account so data cannot bleed and can
  be purged independently. ⚠️ **The per-account _path_ is already v0.1 work and is built** — new
  code must not assume a single fixed database path
  ([`@leapsake/store-layout`](../packages/store-layout/README.md)). What remains is the
  multi-user surface on top of it: a login picker, switching, and per-user purge.
- **User-toggleable encryption beyond custody.** Opting _out_ while holding an account — trading
  end-to-end encryption for server-side features like server-side search — is a **trust-model
  fork, not a free dial**. This argues against per-field content-key encryption on new entities:
  encryption should trend toward a user-level **layer** choice. It is also the reason
  [`@leapsake/key-custody`](../packages/key-custody/README.md)'s custody vocabulary keeps the account axis and the file axis
  separate, even though they always agree today.
- **Finer sharing granularity.** For v0.1 it is acceptable to share People and Pets at the coarse
  grain that pulls in Milestones, Contact Methods, and Relationships. Per-structure granularity is
  a future iteration. (Reminders are **not** a share target.)

## Client / UX

- **`duplicates.findFor` is O(n²) and runs on every person-page load** _(measured
  2026-08-12, by the web spike)_. `findDuplicateCandidates` is a full in-memory pass over
  every pair, filtered to the one person afterwards — and the person screen only uses
  `.length` of the result, to decide whether to show a banner. Measured: **2.1 ms at 100
  people, 122.9 ms at 1 000, 11 781 ms at 10 000**, against 0.8 ms for the other six loader
  calls combined. It is synchronous CPU work, so it stalls the whole process exactly as
  Argon2id does. **This is a desktop bug as much as a web one** — desktop makes the identical
  call on the same screen against its own store; the spike is only what happened to measure
  it. The cheap fix is a count-shaped query for the banner; the real one is an index, since
  the O(n²) pass is fine at personal-CRM scale and nothing else.
- **Styling / the design system.** Now that the UI extraction is done,
  [`@leapsake/ui`](../packages/ui/README.md)`/tokens` grows real values and the components grow
  styles. Markup moved out of the renderer deliberately unstyled, so this is the first pass where
  appearance changes at all. **Partly gated on the web framework**, which also decides CSS Modules
  vs. `transpilePackages` — see [`web-client.md`](./web-client.md).
- **i18n proper.** The catalog seam is built and no component holds a string. What is missing is a
  library, plus `@leapsake/schema`'s English label tables (`genderLabel`, `kindDefs`, the role
  labels), which mobile reads directly. A cross-client workstream, not a UI-package task.
- **Let onboarding nudges notify** _(owner, 2026-08-24)_. `planNotifications` bars them today
  (`onboardingRouteOf(r.id) === null`, `packages/notifications/src/planner.ts`), on the principle
  that "come do something in the app" prompts don't get to interrupt you _outside_ the app. The
  case for revisiting: a user who turns notifications **on** and then never finishes onboarding
  has opted into being told things, and finishing setup is the one thing that makes the rest of
  the app work for them. The running-out notice already carves one exception to that rule — but
  on a narrower basis (a _service notice_: something you asked for is about to stop), so it does
  not settle this. Not urgent; the line to hold either way is service notice vs. re-engagement.
- **Notification privacy levels.** `notification_settings` (migration 29) deliberately has no
  `privacy` column — notification text carries full context today and trusts the OS's own
  lock-screen preview setting. Owner has it as a future want; adding the column later is a cheap
  migration, and guessing its shape now was not worth it. See
  [`@leapsake/notifications`](../packages/notifications/README.md).
- **iPad layouts are phone-shaped** _(owner, 2026-09-13: v0.1 supports iPad)_. `supportsTablet`
  has always been `true`, so the App Store listing is universal and reviewers test on an iPad —
  but every screen was designed at phone width, so a 13" iPad gets phone layouts stretched across
  it. That is _acceptable_, not _good_: nothing is unreachable or broken, and the alternative
  (dropping to iPhone-only) is a one-way door, since removing a supported device family from a
  shipped app strands the people who installed it there. What is deferred is the design work —
  multi-column lists, a split view on the person screen, and a look at the four pickers, which
  are the components most likely to look wrong at width.
  > ⚠️ **Nothing automated has ever run on an iPad.** `scripts/lib/mobile-harness.mjs` → `boot`
  > matches `iPhone` specifically, because the flows are phone-shaped. An iPad tier is additive
  > (the same catalog, a different device), but it is not free: every `tapOn` point-percentage in
  > the flows was measured at phone aspect.
- **Mobile: the last-device Forget-account confirmation needs a `KeyboardAvoidingView`.** The
  keyboard covers "Delete all data". The screen scrolls, so it is reachable by hand, but it is the
  one step of the custody cycle no automated flow can drive — dismissing the keyboard first does
  not help, because the layout reflows and the tap lands on whatever moved under it. **Fix this
  screen before trying to make that cycle an E2E flow**
  ([`apps/mobile/maestro/README.md`](../apps/mobile/maestro/README.md)).

## Encryption, sync, and the relay

Design lives in [`encryption/`](./encryption/); this is only what is unbuilt.

**First, and before anything else in this section: rebuild the client half of sync.** The
platform-neutral half is all still here and tested — `@leapsake/sync`, `apps/server`,
`@leapsake/key-custody`, and the relay orchestration in core — but both clients' flows, settings
screens and relay tests were deleted on 2026-09-17. They are at the tag `relay-clients-final`,
and _how they should be built next time_ is **The rebuild** below. **Do that before building on
top of sync**; everything else in this section assumes it has happened.

**Near-term, none of it blocking:**

- **Shared cross-process rate-limit counter.** Today's limiters _and_ the session store are
  in-memory and per-process; a multi-node relay collapses them.
- **Relay disposability** ([`encryption/sync.md`](./encryption/sync.md) §2): losing `relay.db`
  must never lose user data. Content already lives on devices — close the gap by having devices
  **self-heal the account row + recovery escrow** on sync, so a relay wipe costs one re-join.
- **CK revocation / GC on entity delete** — sync-era cleanup that stops orphaned keys.
- **True background-fetch sync**, plus a configurable sync-interval UI.
- **Cleanup:** `createCore(driver, keySession?)` no longer reads its key session. The parameter
  and the clients' "rebuild the core around the adopted MK" plumbing are inert. Left in place on
  purpose (photos are layer 3's real consumer), so **simplify it whenever layer 3 next gets
  attention.**
- **Relay backup capability** — the client half is built (`fetchRelayCapabilities` GETs
  `/capabilities` and falls back to "no"); the **server** side is undecided, so no relay serves it
  and every user sees the last-device deletion warning. That default is the safe one.

**Still-open security findings** _(from the adversarial review of 2026-07-05; the closed ones —
bootstrap throttling, session tokens, TLS, the convergence DoS — are in `git log`)_. None gates
v0.1, because v0.1 sync is self-host-only and the operator is the user themselves:

- **Raise the Argon2id cost.** The interactive-login floor is doing duty as the _encryption_
  strength — the reasoning and the fact that `KDF_ALG` versioning makes a bump free are in
  [`../packages/crypto/README.md`](../packages/crypto/README.md) → _Pinned algorithms_. Needs one
  measurement of Hermes headroom, then a number.
- **Wipe the KEK and transient wrap keys after use.** The master key cannot be zeroized in a GC'd
  runtime and that is an accepted limit (`packages/key-custody/src/session.ts`), but the KEK is
  derived-then-used-once in `enableSync`/`unlock*` and is cheap to clear. Audit the log and
  error paths in the same pass, so no key-bearing object can be stringified into a crash report.
- **Local backpressure on recovery-phrase entry.** The relay throttles the recovery routes well;
  on-device `unlockWithRecoveryKey` and the phrase-entry UI gate the master key with no attempt
  limiting at all. Less urgent than the password path (the phrase is 256-bit), but the asymmetry
  is the point: passwords get a 12-char floor plus Argon2id, the phrase gets neither locally.
- **Per-device relay credentials and replay defense.** Revoking one device still means changing
  the password, because the credential is per-account. Sessions are also per-process in-memory,
  so a multi-node relay needs a shared session store — the same shape of fix as the rate-limit
  counter above. Sequence this with _Device management_ below.

**v0.2 proper _(owner, 2026-07-27)_:** **automatic locking on idle, and the bounded session.** The
deliberate half (sign out) is built. A real session needs mid-session re-lock in the desktop main
process and in mobile's bootstrap, and it must not be theater, since the keychain still holds the
db-key. Not a one-way door — it sits on the same password door. Deferred with it: **session
lifetime and its dial**, **biometrics on mobile** as the everyday unlock with a true expiry still
demanding the password, and **auto-purge of an idle logged-in device**.

**Post-launch, in dependency order:**

1. **The web app — Stage 4** (SSR split-session rendering + PWA): the no-JS accessibility floor,
   and the render vehicle every URL-based share needs. **Low retrofit risk — now observed, not
   asserted**: the spike server-rendered a person's page _and_ all of person CRUD with
   JavaScript disabled, over a real split session key and with zero package edits, and the
   measurement chose a **cold store with a warm key** — so §9.2 holds as written and no warm
   decrypted store is needed. [`web-client.md`](./web-client.md) is what proves it
   before the architecture hardens; its findings become this increment's plan. Two things it
   hands over: the `authVerifier` must be wrapped under the session key rather than held
   beside it, and **the relay must compact** (or `pull` must collapse by row id) before a
   cold-per-request host is viable, because such a host re-pulls the account's whole write
   history on every request.

   **It ships sync-account-only, and that is a product constraint rather than a technical one**
   _(owner, 2026-08-15 — [`encryption/model.md`](./encryption/model.md) §10.1)_. Browser storage
   is evictable at the browser's discretion — `persist()` was refused even on an **installed**
   PWA — so the web client must never hold the only copy of anything. Desktop and mobile keep
   the local-first promise; web is a view onto an account, and eviction there costs one Argon2id
   and a re-pull instead of the account. Two consequences for this increment: there is **no
   local-only / try-before-signup mode on web**, and every web user implies server storage, so
   it lands on whatever the pricing model turns out to be
   (`../leapsake-monetization.md`). The unclosed edge is **offline writes not yet pushed**,
   which requiring an account shrinks but does not remove — this increment owes an honest
   indication of what has reached the relay, and may owe a decision not to offer extended
   offline _writing_ on web at all.

2. **Capability-link sharing** — zero-knowledge public links (key in the `#fragment`, no
   `key_wrap` row). **Built and observed by the spike** — the key never reached the server and
   the page it served held ciphertext only — so what is left is productizing it: where a share
   row lives (owner's store vs. a new relay table), revocation and expiry (§11's other two
   modes, both unexercised), and a **read-only mode for shared screens**, which today still
   offer Edit / Delete to a stranger. Needs the web app as render vehicle **and** the share-URL
   decision below.
3. **Stage 3 — authenticated sharing**: account keypair + public-key directory (TOFU-vs-verify
   trust) + constrained principals (hosted links, Alexa, CardDAV). Kept entirely post-web. **Needs
   an external crypto audit before public ship** — the recorded review is an internal design audit.

   Three tables are designed but unbuilt, and they are **purely additive** — no shipped table
   changes shape, which is what lets this wait. A **`share`** row is the _access policy_
   (`content_key_id`, `kind ∈ capability | hosted | authenticated`, `expires_at`, `max_visits`,
   `visit_count`), deliberately separate from `key_wrap` because it is a different kind of trust:
   the server honestly refusing to serve, rather than cryptography
   ([`encryption/model.md`](./encryption/model.md) §12). Its `kind` selects the key story —
   `capability` → no `key_wrap` at all (the URL fragment); `hosted` → a wrap to a
   `server_principal`; `authenticated` → a wrap per recipient. A child **`share_grant`**
   (share_id, account_id) carries the allowed accounts, and **`server_principal`** (id, label,
   public_key) registers each constrained reader as a sibling of `account`. All three take the
   standard sync-safe substrate; soft-delete is revoke. Lighting them up also starts writing the
   `principal_kind` values already enumerated in `packages/schema/src/key-wrap.ts` —
   `recipient`, `server_principal`, `session` — which is the whole reason that enum was written
   in full up front.

4. **Hosted-relay gate** — before any official or paid relay stores other people's data: **OPAQUE**
   login, Tier-1 server-escrow recovery (email/password reset as an opt-in dial), quotas /
   registration-token enforcement, and the shared rate-limit counter above.

   **Why OPAQUE is a gate rather than a polish item.** Today the relay receives the raw auth
   verifier on every authenticated request and permanently stores `kdfSalt` and
   `wrap(MK, KEK)`. An operator — or anything at TLS termination, or an access log that captures
   headers — can therefore run, entirely offline and per candidate password:
   `guess → Argon2id → HKDF auth branch → compare to an observed verifier`, then on a hit
   `HKDF kek branch → unwrap wrap(MK, KEK) → decrypt the account`. So "zero-knowledge against
   the relay" currently reduces to _password strength stretched by one interactive-strength
   Argon2id pass_ — which is true enough when the operator is the user, and not true at all the
   moment it is us. Session tokens (built) shrink the observation window to once per login;
   OPAQUE is what makes the claim hold against the adversary the model actually names. The
   decision, the alternatives weighed, and the honest residual — a maximally malicious operator
   can still _actively_ grind with its own OPRF key — are in
   [`encryption/sync.md`](./encryption/sync.md) §4 _Auth-hardening decision_. A client-held
   Secret Key pepper would close it fully and was **declined as a default** (a second user-held
   secret breaks password-only join); at most an opt-in dial, after passkeys.

5. **Custody doors, in preference order** _(decided 2026-07-05)_: **passkeys (WebAuthn PRF)** as an
   additional unlock door — supported, _not_ the default. A 1Password-style Secret Key is
   deliberately **not** planned as a default. Also the high-entropy sync-code / QR-pairing door,
   and username reconciliation across relays.
6. **Device management** — per-device revocation and master-key rotation (the lost-phone story).
   **Grows in importance with photos, so track it before then.** Carries one leftover from the
   account merge: **does a retired local account leave a tombstone?** Retiring it in the roster is
   enough for the device, but nothing yet decides whether the relay should learn that a local
   account id was folded into a synced one. Nothing depends on it today; it starts to matter as
   soon as a user can enumerate their devices.

_Open, each tied to a not-yet-started stage:_ the **asymmetric scheme** (X25519/Ed25519, Stage 3);
the **public-key directory trust model** (TOFU vs. verification, Stage 3); the **web framework**
(Stage 4 — the spike deliberately does not settle it); **share-URL formation** across self-hosted
instances at arbitrary domains; **metadata minimization** (out of scope for V3 — revisit before
privacy-first marketing at scale, and again before photos); and a **confidential-computing enclave
for SSR**, the Stage 4 ceiling.

## Files and media — encrypted blobs, photos first _(the v0.2 headline)_

Nothing built. **Photos are the first consumer, not a special case**: one blob pattern for every
file type (then video, documents, audio), the same privacy as rows (encrypted on-device, hosts
store only ciphertext, offline-first), SaaS-grade convenience (resumable background upload, fast
gallery, sharing — the encryption stays invisible), and **bulk export of originals** as a
first-class exit story. Crypto it rides on: [`encryption/model.md`](./encryption/model.md) §3
(envelope), §11 (sharing/blobs), §12 (limits).

Photos are also layer 3's real consumer, so the `createCore` cleanup above waits on this.

### The invariants — pinned before code exists, on purpose

So v0.2 cannot weld photo-specific decisions into what must stay a generic file layer:

1. **Blobs never ride the row-sync channel.** Rows (`EncryptedRecord`) sync small sealed JSON;
   file bytes move over a **separate, content-addressed blob channel**, so a multi-GB payload
   cannot block or bloat row convergence.
2. **A `file` row references the blob; bytes live elsewhere.** The metadata row (id, blob ref,
   size, MIME, dimensions/duration, wrapped CK) is an ordinary syncable entity — one
   `defineSyncable`, LWW untouched. The reserved `wrappedKey` field on `EncryptedRecord`
   (`packages/sync/src/transport.ts`) is the hook: the row escalates to a per-item content key,
   and that same CK encrypts the blob.
3. **Chunked + resumable from day one.** Mobile background limits make non-resumable uploads fail
   at real library scale. Encrypt per-chunk with the chunk index bound into the AEAD's AAD (no
   silent reorder or drop), so a resume re-sends only missing chunks.
4. **All derived data is client-computed and encrypted.** Thumbnails, previews, waveforms,
   extracted text, embeddings, face clusters — a zero-knowledge host cannot generate them and
   **must never be able to** (a thumbnail or embedding leaks nearly as much as the original).
   Clients compute on-device and store them as encrypted blobs/rows, mirroring how search and
   kinship already run on in-memory plaintext.
5. **Storage lives behind a `BlobStore` port** — the same adapter-swap discipline as
   `SqliteDriver` / `KeyStore` / `SyncTransport`. Filesystem adapter first, S3-compatible for the
   hosted era, BYO bucket as the endgame. The relay or object store holds ciphertext chunks +
   access policy, **never keys**.

**Falls out for free:** sharing, revocation/expiry/visit-limits, and P2P all reuse the row
mechanisms unchanged — wrap the blob CK for a recipient, a `#fragment`, or a server principal;
the host refuses to serve chunks; ciphertext over an untrusted pipe, and content addressing even
suits P2P swarming.

### Honest costs, accepted going in

- **Metadata leaks more.** Blob count, size, and timing say more than row counts. Still out of
  scope to hide; re-examine before scale claims (padding and bucketing are the tools).
- **Client-side compute.** Thumbnailing and ML run on-device — thumbnails are cheap, embeddings
  and face-grouping are optional and not launch-gating.
- **Hosting economics.** Ciphertext blobs cannot be cross-user deduped or compressed, so quotas
  and the registration-token seam become load-bearing in the paid-relay era.
- ⚠️ **The no-JS floor vs. media.** Serving decrypted media to a no-JS browser means the render
  server transiently holds _file_ keys, and whether media is exempt from that floor is
  **undecided**. The web spike's SSR measurements are the input to this decision.

### The sharing question that shapes the schema _(raised 2026-07-27)_

A shared album is **bytes plus rows** — timestamps, location, and "who is in this photo." Two
consequences are easy to foreclose by accident, so decide both **before** the `file` schema is
written:

- **CK scoping.** `content_key` currently enforces _one CK per entity_. An album is a sharing
  unit spanning many rows _and_ blobs, which wants one CK per **unit**. A migration, not a
  re-encryption — but check it first ([`encryption/model.md`](./encryption/model.md) §2.2, and
  the warning on `contentKeySchema` in `packages/schema/src/content-key.ts`).
- **People tags — unsolved, and a data-model question rather than a crypto one.** "Who is in this
  photo" points at a Person row the recipient may have no right to read. Sharing an album with
  tags either leaks a contact reference or needs a **projection**: share the name, not the person
  record. **Do not let the file schema assume a shared album can dereference the owner's People
  rows.**

### Open, decide at build time

- **Chunk format** — size, AEAD framing, an existing streaming format (age/STREAM) vs. an
  in-house seal with indexed AAD.
- **Content addressing vs. dedup** — address ciphertext (no cross-file dedup, no equality leak)
  vs. convergent plaintext hashing (dedup, but equality observable). **Lean: address ciphertext**,
  and dedup client-side via a local plaintext hash in the `file` row.
- **Where derived data is computed** — first device to hold the original? opportunistically? do
  embeddings sync or recompute per device?
- **Platform transfer machinery** — iOS `URLSession` / Android WorkManager vs. app-level chunk
  loops. Interacts with the sync scheduler.
- **Quotas and the policy surface** for the paid relay (per-account storage, max blob size).

## Gifts — what the v0.1 scope cut removed _(owner, 2026-08-20)_

Gifts were **cut back to four sentences** the day after the occasion work landed: log an idea,
attach it to one or more people or pets, mark a pairing given, keep a name and a URL. Everything
below was built, worked, and was deleted — see `361fc1d` for the cut, and `41ee888` / `476660b`
for the model as it stood. Nothing here is a bug or an omission; each is a decision to re-make
later, on purpose, with the code one `git show` away.

⚠️ **Unlike everything else in this file, restoring these now costs a real migration.** They were
removed under the pre-v0.1 latitude, which expires at v0.1 — after that there are users, and
`gift_recipients` has to be widened rather than replaced.

- **Occasions** — the whole apparatus. A gift could name a milestone, a holiday, or (on an idea)
  a bare milestone _kind_, from a pool that was **ranked rather than filtered** across three
  tiers, and picking something the party did not have yet **created it** — the holiday
  observance, or a dateless milestone. That last part is the piece worth remembering: "Anna gets
  a Christmas gift" and "Anna keeps Christmas" were treated as the same fact, so the user never
  had to say it twice. `materializeOccasion` in `packages/core` was where it happened.
- **Dates, in both tenses** — a suggestion's `target_*` (intent: "for Christmas 2026") and a
  giving's plain `year`/`month`/`day` (what happened), on the milestone partial-date shape. With
  them went the "When?" shortcut row (`gift-when.ts`), which offered a couple of plausible years
  per tense rather than three number inputs.
- **Repeat givings.** The scotch you give your dad every Christmas was one suggestion and N
  dated gifts. It is now one ticked box; that it happened more than once is unrepresentable.
  **This is the case the three-table split existed for**, so re-adding dates and re-splitting are
  the same task.
- **The giver.** `gifts.giver_*`, nullable, meaning "unknown who gave it" — _not_ "me", since "I
  gave it" pointed at the `self_person` singleton. It is the schema half of received /
  third-party gifts, which the UI had already deferred. Dropping the column turned that from a
  v0.2 _screen_ into a v0.2 _migration_.
- **Idea-level occasions** (`gift_idea_occasions`, migration 34) — "this would make a good
  Christmas gift for someone", said with nobody named. Its own table because a candle is a
  birthday gift _and_ a housewarming gift, and a row per occasion merges where a column drops one
  under LWW. It was also the only place `occasion_type = 'kind'` was ever stored.
- **The "when is Anna's birthday?" nudge** — never built, and now has nothing to hang off. A
  dateless milestone created by picking an occasion was a question the app knew to ask; it would
  have been a fifth `SYSTEM_REMINDER_NAMESPACE` (`undated:`) alongside `milestone:` / `holiday:` /
  `onboarding:` / `duplicates:`.

Two supporting pieces went with them and would come back the same way: `HolidayEntry.giftGiving`
(a display-only catalog flag, outside the byte-pinning test, needing no `CATALOG_VERSION` bump)
and `isGiftBearingKind` (derived from a kind's own schedule offering a `gift` action, rather than
a second list that could disagree). The `moved` milestone kind and graduation's `gift` schedule
action were added alongside them but are **kept** — they are true about reminder schedules on
their own terms.

Also unbuilt, and unaffected by the cut: **suggestion → reminder** (a target date was never a
nag; the `due_date` + `@mention` escape hatch has no affordance on either client), **URL-first
title derivation** (waiting on the share target / browser extension that motivates it), and
**near-duplicate idea merging** via the reconciliation substrate.

## Reminders — deliberately unbuilt

How the shipped engine works — the prompt, the windows, the `verb:qualifier` identity split — is in
[`@leapsake/reminders`](../packages/reminders/README.md). This is only what was deferred.

⚠️ **Read that README's _Schedules_ section before any of these tempts you toward a per-person or
per-kind default.** The four-level cascade was cut on 2026-09-05, and the argument against it — plus
the four things a second writable level would drag in — is recorded there.

- **The offer-set differ.** An answered prompt stores the **full** set it was offered, so the record
  of what was offered already exists; nothing compares it against today's set, so an action that
  becomes available later never re-asks.
- **The holiday prompt.** The per-bearer shape is right for milestones and wrong for holidays, where
  one occasion spans everyone: Christmas wants a single prompt listing people, not one per
  observance. Same writes through the same path, different presentation. ⚠️ **Do not ship
  per-observance prompts in the meantime** — forty Christmas questions in November is worse than the
  noise the prompt exists to cure.
- **Batching milestone prompts — declined** _(owner, 2026-09-11)_. Three birthdays in one
  fortnight stay three `plan` rows, and so does a contact import that raises thirty at once. A
  milestone's question is about **one person or pet and one occasion**, because that is the unit
  the decision is made in: "you have 12 birthdays in the next 6 weeks" is borderline inactionable,
  since nobody decides what to do for twelve people at once, only for Violet, then for Harry. The
  import flood that made batching tempting is a **timing** problem, not a grouping one — a
  question that arrives inside its own lead time was being shown as already late — and was fixed
  on the question's deadline instead (2026-09-11; the reminders README, _You can't be late for
  something the app has only just learned_). ⚠️ A communal question is
  right only where **one occasion genuinely spans everyone**: the holiday prompt above ("let's
  make a plan for sending holiday cards") is that case, and stays the only one. Do not reuse its
  shape for person-specific milestones.
- **Presets — one human question instead of typed offsets. Considered and declined** _(owner,
  2026-09-05)_. "Am I seeing them, or posting it?" picks a rule set: posting wants the gift further
  out and the card in the post a week ahead; seeing them wants neither deadline. With no person
  level to hang it on it could only ever be a **second question on the prompt**, never a surface of
  its own — and the prompt's tickboxes already say _what_ you will do, so all this adds is moving
  the dates by a few days. That is a poor trade against the design's stated risk, that answering
  the prompt must stay a five-second decision (the README, _A question costs more than a row_).
  **The trigger for revisiting** is real use showing the posted-card deadline actually bites: one
  set of offsets that runs slightly early for people you will see is the accepted cost until then.
  ⚠️ If it returns, whatever picks the numbers does the arithmetic itself and stores plain offsets
  (the README, on rule dependencies).
- **Channel-aware reminder copy** — "Text A happy birthday" where a number is the only way to reach
  someone. Dropped with the channel actions _(owner, 2026-09-05)_: it needs a `reach` port on the
  engine, sentence variants beside `actionDefs.wish`, and a `@leapsake/contact-links` dependency in
  `@leapsake/core`. The ways to reach someone are buttons rendered from `reminders.targets` instead.
- **A configurable in-person deadline** _(owner, 2026-09-11)_. A gift or card started too late to
  post slides to the day before the occasion, to be handed over in person (`latestOffsetDays` on
  `actionDefs`). The owner wants that day configurable eventually; it is one literal until there is
  somewhere to set it.
- **Per-action grace periods**, **snooze for user reminders** (the open question on
  `partitionReminders`' doc-comment), and **user-defined milestone kinds**.

## Holidays — doors deliberately left open

How the shipped feature works is in [`@leapsake/holidays`](../packages/holidays/README.md), which
also describes the mechanisms each item below would use. The design admits each **additively**,
which is why they were deferred rather than built.

**One calendrical task with a real deadline:** re-derive the eight lunisolar tables before ~2050.
They run to 2056; see `packages/holidays/src/catalog.ts`.

- **Islamic holidays** (Eid al-Fitr, Eid al-Adha, Ramadan) — **consciously skipped, not missed.**
  The dates depend on moon _sighting_ and differ by country and authority, so no computation yields
  one correct date. The three options weighed were: tabulate Umm al-Qura and state that the local
  date may differ by a day; one entry per authority as a `familyId` family; or a "date may shift"
  flag, the only one of the three that is not purely additive. Meanwhile **hide + create** already
  composes an answer for anyone who needs a specific authority.
- **Hindu and Buddhist holidays** (Diwali, Holi, Vesak) — blocked on **sourcing, not effort.**
  There is no second independent implementation to check these against the way ICU checks the
  Hebrew and Chinese tables: ICU's `indian` calendar is the Saka _solar_ calendar, not the
  lunisolar panchanga Diwali needs. The civil date turns on which day the tithi prevails at
  sunrise, with genuine Amanta/Purnimanta regional variation, and published almanac dates do not
  reach the 2056 horizon. **Do not author these from a single computation** — every other table in
  the catalog was gated against exactly that.
- **Holiday reminders with no Person attached** ("get a tree"). The bearer-type enum and disjoint
  id namespaces admit `holiday` later with no schema change.
- **Aggregate / grouped reminders** — collapsing "40 Christmas cards" into one row. ⚠️ **The one
  non-reversible item here**: an aggregate is a different deterministic id, so migrating later
  loses completion state. Related and _reversible_: **synchronized load** (everyone's Christmas
  reminders come due at once, unlike birthdays) — ids key on occurrence + action, not surface
  date, so it can be tuned whenever it starts to hurt.
- **User-defined holidays authoring UI.** The schema has been capable from day one; expected <1%
  of users.
- **Religions / Nationalities fields** as bulk-assignment accelerators, with the inference
  constraints the package README pins.
- **Observed-date shifting** (holiday falls Saturday → observed Friday). Matters for "office
  closed", barely for gifting. **Leaning skip**; noted, not solved.
- **Per-user greeting overlay** — "Happy Christmas" for a British user. An overlay, never an edit
  to a read-only catalog row.
- **@-mentioning holidays.** Not free (the `mentions` table references entity UUIDs; holiday
  identity is slug-based) and not a priority. The better shape for the underlying idea is
  natural-language date detection — "on Christmas" fills the due date.
- **Events** — user-defined, separate-but-related to Milestones and Holidays. Much further out.
  The motivating distinction: _"my family does a thing on August 3rd"_ (an Event) vs. _"my family
  observes an obscure holiday on August 3rd"_ (a user-defined Holiday).

## Platform and tooling

- **Desktop local-notifications applier.** `@leapsake/notifications`'s planner and reconcile are
  platform-free by design, and `notification_settings` is device-keyed precisely so an Electron
  applier (`Notification`) drops in later — mobile-only for v0.1. A device with no row is `off`, so
  desktop simply does not appear under _Other devices_ until it ships one.
- **Windows / Linux desktop.** Out of scope for v0.1, matching the E2E host policy — blocked, not

### Making a release re-run idempotent

_Moved here from `v0-1_10_external-testflight.md` on 2026-08-28, on that doc's own
instruction: it did not land with the beta rung, so it does not get to sit in a v0.1 doc.
Scoped to `scripts/release/index.mjs`. Nothing about it blocks a beta — the failure it
prevents costs a wasted build number, not a wrong one._

**The goal:** a release is all-or-nothing across every ready target, and the recovery for any
failure is to fix it and run **the same command again** — never `--only`, which is to be
retired as a routine tool.

For **test** failures this is already true and needs nothing: the gate runs one repo-wide
suite, so a red iOS tier aborts before any tag exists and restores every manifest. Proven on
`alpha.2` (`v0-1_06` §B, since deleted).

The gap is the phase **after** the tag, which is per-target (`index.mjs`'s ship loop). If iOS uploads
and Android fails, there is a tag, one shipped platform and one not — and a bare re-run
computes the _next_ number rather than retrying, then re-uploads the platform that already
succeeded. Two changes close it:

- **Resume the existing tag instead of minting a new one** when the previous release did not
  finish. Largely derivable: after a partial release HEAD _is_ the tag and the manifests
  agree, which is already the `--from-tag` precondition.
- ✅ **Record which targets shipped** _(built 2026-09-13)_. `scripts/release/receipts.mjs`
  writes one JSON line per shipped target to a `refs/notes/releases` note on the tagged
  commit, carrying the tag, target, build number and bundle id. It was built for the other
  caller — going live needs the commit behind the build Apple approved — and answers this
  one for free: `shipmentsFor(root, commit)` is "which targets already shipped, under which
  build number". What is still owed here is the _resume_ half above, which has to read it
  and skip a target that already succeeded.

⚠️ **Gate platforms in the registry, never with a flag.** This is what `--only`'s retirement
depends on: when the Android target flips to `ready`, a bare `pnpm release <rung>` would upload
to Play — and the _first_ such upload permanently claims `com.leapsake.app` for whichever
account made it ([`android-pipeline.md`](./android-pipeline.md)). That belongs in `android.mjs`
as a `blocked` status or a failing `requires` check on the rung — something the release refuses
and explains — not in a flag someone has to remember to leave off.

### The N-API exit from the SQLite ABI dance

**A watch-item, blocked upstream. Nothing to build yet** — this exists so the exit is recognised
the moment it becomes available instead of being re-derived. How the problem bites day to day,
and how to recover from it, is in [`../AGENTS.md`](../AGENTS.md) → _The native SQLite ABI_.

The desktop at-rest driver is a native module (`better-sqlite3-multiple-ciphers`) whose prebuilt
`.node` is compiled against a single `NODE_MODULE_VERSION`, and we load it from **two runtimes
with different ABIs** — Electron and Node (Vitest integration tests deliberately run against the
real production engine). One binary, two ABIs, so whichever ran last wins.
`scripts/ensure-sqlite-abi.mjs` papers over it. This is the cost knowingly accepted when at-rest
encryption overrode the native-module-free `node:sqlite` preference
([`encryption/model.md`](./encryption/model.md) §8).

**The exit:** [better-sqlite3 v13](https://github.com/WiseLibs/better-sqlite3/releases/tag/v13.0.0)
(June 2026) rewrote the addon onto **Node-API**, which is ABI-stable across runtime versions —
one `.node` loads under both Node and Electron. That **deletes the problem class**, not mitigates
it.

**Why we cannot take it yet:** we depend on the encryption fork, not upstream, and it has not
rebased — `better-sqlite3-multiple-ciphers` is at **12.11.1** with no v13 branch, still shipping
per-ABI prebuilds. Switching to upstream is not an option: the fork _is_ the
`PRAGMA cipher`/`PRAGMA key` support the whole at-rest design rests on. It historically tracks
upstream releases, so this is _watch, then take_ — not a fork or a patch.

**When it lands:** bump to `^13`; delete `scripts/ensure-sqlite-abi.mjs`; strip its prefix from
the desktop `dev`/`start`/`rebuild` scripts and from `pnpm test`; re-check packaging (one
ABI-agnostic binary should _simplify_ asar unpacking); verify the cipher pragmas are unchanged
(`applyDatabaseKey`) and the driver contract passes on both runtimes with no rebuild step.
**Verification:** run `pnpm test` and the desktop app back-to-back in either order with no
rebuild between. Today that is exactly what fails.

**Non-scope: mobile.** `apps/mobile` uses `expo-sqlite` (SQLCipher path), a native module
compiled by RN's own toolchain — no `NODE_MODULE_VERSION`, never shared a binary with desktop.

- **Two-instance E2E (Flows 6, 7a)** — deferred out of v0.1 ([`testing/crucial-flows.md`](./testing/crucial-flows.md)), which defers them out
  of the v0.1 gate.

### The website's edge is untested — a live smoke tier

**A gap, not a bug.** `apps/website/test/site.test.ts` asserts the **build artifact**, and
Cloudflare rewrites the response **after** the build. Everything the suite proves is therefore
true only up to the edge, and the two things it proves hardest — the policy carries its contact
address, and the site ships no JavaScript — are exactly the two that were false in production
while the tests were green.

Both were found by eye on 2026-08-30, not by a check:

- **Email Address Obfuscation**, which is **on by default for a new zone**, rewrote
  `hello@leapsake.com` into `[email protected]` and injected a decoder script. A reader without
  JavaScript saw no contact address at all — on the document App Store Connect points at, whose
  only stated contact method is that address.
- **Cloudflare RUM** injected a `static.cloudflareinsights.com` beacon, which Firefox reports to
  visitors as _"1 tracker blocked"_ — on the marketing site for a product whose pitch is that it
  contains no trackers. Cookieless and aggregate-only, so the harm was to the claim rather than
  to anyone's privacy, which is its own kind of expensive.

**The check to build:** fetch `/` and `/privacy/` and diff them **byte-for-byte against
`dist/`**. Stronger than asserting the absence of any particular injection, because it needs no
list of features to watch: any future Cloudflare default that flips on is a byte difference.
Both pages matched exactly once the two settings were off, so the equality is real and not
aspirational.

⚠️ **The trap that makes this worth writing down.** The beacon is injected **only for
browser-shaped requests** — `Accept: text/html` plus `Sec-Fetch-Dest: document`. A plain `curl`
returns the clean page, so a naive check passes while every real visitor gets the script. It
also appeared only on the custom domain, never on `*.pages.dev`, which is what localised it to
the zone rather than the Pages project.

**Why it is not built yet:** it puts the network in the test path. It belongs as a
manually-run tier (`test:live`) that never joins `pnpm test`, in the shape of the existing
static guards — or, less good, as a periodic check.

Until it exists, two Cloudflare toggles are all that hold this, and **nothing records which
ones**: `apps/website/README.md` does not yet name the features that must stay off. That is the
cheap half of this item and worth doing first — a checked equality is better than a note, but a
note is better than remembering.
