# Leapsake v0.2 and beyond — everything that is not v0.1

> **The rule that fills this file:** if it does not *gate* v0.1, it waits. Several items below
> are ready to build and merely non-blocking — that is not a reason to pull them forward. See
> [`v0-1.md`](./v0-1.md) for what does gate, and why the list is kept short enough to finish.

Nothing here is ordered against anything else unless it says so. Each section is independent.

## Ready now, deliberately held

Built or nearly-built work whose only obstacle is that it is not a v0.1 gate.

- **vCard / JSContact export.** The portability and exit-strategy answer: user-initiated,
  client-side (the client already holds plaintext), people + contact methods first. Cheap, and it
  doubles as groundwork for a future CardDAV surface. **It also redeems a promise already made** —
  `encryption/model.md` §7.3.1 says Forget-account should offer an export first, and today
  desktop's hard-confirm can only tell the user to copy their `stores` folder while mobile cannot
  say even that. Wire the real offer when the exporter lands.
- **Reminder search.** Reminders join `SearchResultType` the way gift ideas did, matched on title
  + body. The last piece of the reminders surface.
  > Needs a deliberate answer first: **snoozed** rows are hidden from Home — should they be
  > findable by search? See [`../packages/reminders/README.md`](../packages/reminders/README.md).
- **The onboarding import nudge.** `@leapsake/contact-import` already ships vCard drag-drop, so
  this is a step definition, copy, and a CTA route — not new import capability. `applies`: few or
  no people yet; ranks high in step order, below connect.
  > **Sequence it against bulk-import dedup below** — importing 200 people fires the duplicates
  > nudge, and the user should not be handed two chores at once. Whichever lands second reads the
  > other. Also decide whether `add-first-person` and import should ever both apply, or whether
  > import supersedes it.
- **Settings decomposition + an Account screen.** Today both onboarding nudges land a first-week
  user at the top of a ~50KB settings screen and hope they scroll. Split Settings into linked
  sub-screens; give the account flows their own route; extract the account forms so the **same**
  components serve both the Account screen and Settings.
  > Carry [`v0-1_02`](./v0-1_02_account-invitation.md)'s deferred item into this work: the create
  > screen should open by asking *"Do you already have a Leapsake account on another device?"* —
  > it catches every route in, including Settings visited directly, and is the only guard that
  > does not depend on the user reading two Home rows correctly.

## Reconciliation — dedup and merge quality

How the built parts work is in [`../packages/core/README.md`](../packages/core/README.md).

- **Fuzzy / typo-tolerant name matching** — the scorer's reserved `"low"` tier, via
  `fastest-levenshtein` or `cmpstr`, entirely inside `duplicate-score.ts`'s `sameFoldedName`
  predicate. No caller or API change.
- **`libphonenumber-js` phone normalization** — E.164 canonicalization; its own increment.
- **Pets / generalized `mergeEntities`** — a small follow-on; the reference graph is already
  entity-typed.
- **Bulk-import dedup.** Today `ingestContacts` creates every accepted contact unconditionally,
  so importing an overlapping list produces duplicates *after the fact*. Mostly A+B reuse: score
  each parsed contact against the existing set before the review screen renders. The seam exists —
  `ImportDecision.action` is an enum with `create` and `skip`, and this adds a third arm pointing
  at an existing person. **Must honor the `not_a_duplicate` memory**, or a pair the user already
  dismissed comes back on every import.

*Open:* **survivorship granularity** (v1 keeps the survivor's scalar fields wholesale; a per-field
picker is deferred — revisit if users hit it) and **concurrent merges** (two devices merging
overlapping pairs differently may diverge under LWW; noted, not solved).

## Client / UX

- **Styling / the design system.** Now that the UI extraction is done,
  [`@leapsake/ui`](../packages/ui/README.md)`/tokens` grows real values and the components grow
  styles. Markup moved out of the renderer deliberately unstyled, so this is the first pass where
  appearance changes at all. **Partly gated on the web framework**, which also decides CSS Modules
  vs. `transpilePackages` — see [`v0-1_web-spike.md`](./v0-1_web-spike.md).
- **i18n proper.** The catalog seam is built and no component holds a string. What is missing is a
  library, plus `@leapsake/schema`'s English label tables (`genderLabel`, `kindDefs`, the role
  labels), which mobile reads directly. A cross-client workstream, not a UI-package task.
- **Mobile: the last-device Forget-account confirmation needs a `KeyboardAvoidingView`.** The
  keyboard covers "Delete all data". The screen scrolls, so it is reachable by hand, but it is the
  one step of the custody cycle no automated flow can drive — dismissing the keyboard first does
  not help, because the layout reflows and the tap lands on whatever moved under it. **Fix this
  screen before trying to make that cycle an E2E flow**
  ([`apps/mobile/maestro/README.md`](../apps/mobile/maestro/README.md)).

## Encryption, sync, and the relay

Design lives in [`encryption/`](./encryption/); this is only what is unbuilt.

**Near-term, none of it blocking:**

- **Shared cross-process rate-limit counter.** Today's limiters *and* the session store are
  in-memory and per-process; a multi-node relay collapses them.
- **Relay disposability** ([`encryption/sync.md`](./encryption/sync.md) §2): losing `relay.db`
  must never lose user data. Content already lives on devices — close the gap by having devices
  **self-heal the account row + recovery escrow** on sync, so a relay wipe costs one re-join.
- **CK revocation / GC on entity delete** — sync-era cleanup that stops orphaned keys.
- **True background-fetch sync**, plus a configurable sync-interval UI.
- **Cleanup:** `createCore(driver, keySession?)` no longer reads its key session. The parameter
  and the clients' "rebuild the core around the adopted MK" plumbing are inert. Left in place on
  purpose (photos are layer 3's real consumer), so **simplify it whenever layer 3 next gets
  attention.**
- **Relay backup capability** — the client half is built (`fetchRelayCapabilities` GETs
  `/capabilities` and falls back to "no"); the **server** side is undecided, so no relay serves it
  and every user sees the last-device deletion warning. That default is the safe one.

**v0.2 proper *(owner, 2026-07-27)*:** **automatic locking on idle, and the bounded session.** The
deliberate half (sign out) is built. A real session needs mid-session re-lock in the desktop main
process and in mobile's bootstrap, and it must not be theater, since the keychain still holds the
db-key. Not a one-way door — it sits on the same password door. Deferred with it: **session
lifetime and its dial**, **biometrics on mobile** as the everyday unlock with a true expiry still
demanding the password, and **auto-purge of an idle logged-in device**.

**Post-launch, in dependency order:**

1. **The web app — Stage 4** (SSR split-session rendering + PWA): the no-JS accessibility floor,
   and the render vehicle every URL-based share needs. **Low retrofit risk** — the KEK layer makes
   the SSR session-key door additive and the auth-verifier split is already built.
   [`v0-1_web-spike.md`](./v0-1_web-spike.md) is what proves it before the architecture hardens;
   its findings become this increment's plan.
2. **Capability-link sharing** — zero-knowledge public links (key in the `#fragment`, no
   `key_wrap` row). Needs the web app as render vehicle **and** the share-URL decision below.
3. **Stage 3 — authenticated sharing**: account keypair + public-key directory (TOFU-vs-verify
   trust) + constrained principals (hosted links, Alexa, CardDAV). Kept entirely post-web. **Needs
   an external crypto audit before public ship** — the recorded review is an internal design audit.
4. **Hosted-relay gate** — before any official or paid relay stores other people's data: **OPAQUE**
   login, Tier-1 server-escrow recovery (email/password reset as an opt-in dial), quotas /
   registration-token enforcement, and the shared rate-limit counter above.
5. **Custody doors, in preference order** *(decided 2026-07-05)*: **passkeys (WebAuthn PRF)** as an
   additional unlock door — supported, *not* the default. A 1Password-style Secret Key is
   deliberately **not** planned as a default. Also the high-entropy sync-code / QR-pairing door,
   and username reconciliation across relays.
6. **Device management** — per-device revocation and master-key rotation (the lost-phone story).
   **Grows in importance with photos, so track it before then.**

*Open, each tied to a not-yet-started stage:* the **asymmetric scheme** (X25519/Ed25519, Stage 3);
the **public-key directory trust model** (TOFU vs. verification, Stage 3); the **web framework**
(Stage 4 — the spike deliberately does not settle it); **share-URL formation** across self-hosted
instances at arbitrary domains; **metadata minimization** (out of scope for V3 — revisit before
privacy-first marketing at scale, and again before photos); and a **confidential-computing enclave
for SSR**, the Stage 4 ceiling.

## Files and media — photos first *(v0.2 proper)*

Nothing built; the invariants are pinned and the design is in [`files.md`](./files.md), which
survives because it is design rather than a work list. Photos are layer 3's real consumer, so the
`createCore` cleanup above waits on this.

⚠️ **The one cross-cutting question:** serving decrypted media to a no-JS browser means the render
server transiently holds *file* keys, and whether media is exempt from the no-JS floor is
undecided. The web spike's SSR measurements are the input to that decision.

## Holidays — doors deliberately left open

How the shipped feature works is in [`@leapsake/holidays`](../packages/holidays/README.md), which
also describes the mechanisms each item below would use. The design admits each **additively**,
which is why they were deferred rather than built.

**One calendrical task with a real deadline:** re-derive the two provisional lunisolar tables
before ~2050. They run to 2056; see `packages/holidays/src/catalog.ts`.

- **Holiday reminders with no Person attached** ("get a tree"). The bearer-type enum and disjoint
  id namespaces admit `holiday` later with no schema change.
- **Aggregate / grouped reminders** — collapsing "40 Christmas cards" into one row. ⚠️ **The one
  non-reversible item here**: an aggregate is a different deterministic id, so migrating later
  loses completion state. Related and *reversible*: **synchronized load** (everyone's Christmas
  reminders come due at once, unlike birthdays) — ids key on occurrence + action, not surface
  date, so it can be tuned whenever it starts to hurt.
- **User-defined holidays authoring UI.** The schema has been capable from day one; expected <1%
  of users.
- **Religions / Nationalities fields** as bulk-assignment accelerators, with the inference
  constraints the package README pins.
- **Observed-date shifting** (holiday falls Saturday → observed Friday). Matters for "office
  closed", barely for gifting. **Leaning skip**; noted, not solved.
- **Per-user greeting overlay** — "Happy Christmas" for a British user. An overlay, never an edit
  to a read-only catalog row.
- **@-mentioning holidays.** Not free (the `mentions` table references entity UUIDs; holiday
  identity is slug-based) and not a priority. The better shape for the underlying idea is
  natural-language date detection — "on Christmas" fills the due date.
- **Events** — user-defined, separate-but-related to Milestones and Holidays. Much further out.
  The motivating distinction: *"my family does a thing on August 3rd"* (an Event) vs. *"my family
  observes an obscure holiday on August 3rd"* (a user-defined Holiday).

## Platform and tooling

- **Windows / Linux desktop.** Out of scope for v0.1, matching the E2E host policy — blocked, not
  waived. Windows code-signing certs carry their own procurement latency and, for OV/EV,
  hardware-token logistics.
- **The N-API exit from the SQLite ABI dance** — a watch-item blocked upstream, with a written
  trigger and migration. See [`sqlite-abi-napi.md`](./sqlite-abi-napi.md).
- **Two-instance E2E (Flows 6, 7a)**, if open decision 2 in [`v0-1.md`](./v0-1.md) defers them out
  of the v0.1 gate.
